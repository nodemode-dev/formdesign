# The dock's engine contract

Module version 2.2.0. This file travels with the shared dock folder and is the same in every app.

The dock's frontend never talks to an engine. It calls the functions of `DockAdapter` (adapter.ts), and each app's adapter turns them into its engine's routes, sockets or event streams. This file says what an engine has to provide so that an adapter can deliver each function, in words that do not depend on the engine's language. Paths, header names and transports are each app's own. Where a clause says "the adapter", the engine may do the work instead; where it says "the engine", the adapter cannot make it up.

Sixteen clauses. An engine that lacks one says so in its app's port notes and the adapter leaves the matching member out; the module then hides what depends on it.

## Who may call

1. **The caller.** Every route and stream acts for a caller the app identifies by its own means (a window key, a session cookie). Terminal tabs and the Chat conversation belong to that caller, and a list returns only theirs. An agent's credential is never accepted for these routes: the dock is the person's.
2. **Stream authentication is the app's.** A stream may need a one-time ticket, a first message carrying a key, or a cookie. The adapter hides this: `terminal.channel(id)` and `chat.subscribe(handlers)` may take an asynchronous step before the stream opens. A ticket is bought with the caller's own credential, is spent once and expires within a minute.

## Terminals

3. **The record.** `{ id, title, alive, kind }` and optionally `tip`. `id` is opaque and safe in a URL path. `kind` is one of `shell`, `claude`, `codex`, `cursor`, `agent` (a read-only tab showing an agent's commands). `title` is shown as given and is not translated. `alive: false` means the program has ended and the tab is shown struck through. `tip` is the tab's tooltip (a working folder, for example). Extra fields are ignored. `terminal.list()` returns the caller's tabs, oldest first.
4. **Open.** `terminal.open(kind, { cols, rows, prompt?, resume? })` returns the record. `cols` and `rows` are integers the engine clamps without failing. `prompt` is a first message for Claude Code: the engine may type it into a Claude Code tab that is already running and return that tab, so the module accepts an id it already has. `resume` is a Claude Code session id and always makes a new tab. The prompt may be a program argument; a token never is.
5. **Restart.** `terminal.restart(id)` keeps the id, starts the program again and clears the screen. The engine either keeps the stream open across the restart or ends it; the module opens a new channel when the old one has closed. An engine with no restart leaves the function out and the button is not shown.
6. **Close.** `terminal.close(id)` kills the program, is safe to repeat, and succeeds for an id that is already gone.
7. **The channel, engine to window.** `onData` delivers the program's output as text or as bytes, undecoded by the engine; a character may be split across two deliveries when bytes are used. On every attach the engine first replays its scrollback (how much is its choice), and reports `onExit` at once if the program has already ended. `onExit` is an event and nothing is printed for it. The engine sends something on every attach (an empty replay counts if the adapter reports it), because a channel that closes before any data is how the module decides that the engine did not answer.
8. **The channel, window to engine.** `send(text)` is what the person typed, as the terminal emulator encodes it; `resize(cols, rows)` follows every change of size. How these travel (JSON frames, binary frames, separate requests) is between the adapter and the engine. The engine ignores what it does not understand.
9. **The channel, the rest.** Several attachments to one tab are allowed and each gets the replay. For a reader that cannot keep up the engine drops output or closes the stream, never blocks the program. No keep-alive is required. `onClose` after the first data means "closed", whatever the reason. `close()` ends the attachment, not the program.

## Agent programs

10. **Status.** `agentStatus()` answers for the programs the app offers, in one request: `{ claude?, codex?, cursor? }`, each `{ installed, version, install, signedIn }`. `version` is a string or null. `install` is a command line a person can paste, never a sentence, and may be empty. `signedIn` is true, false, or null when the engine cannot tell; the module has a wording for each. A program that is left out is one the app does not offer, and the module says nothing about it. `null` for the whole answer means the engine was not reachable. The call must be cheap enough to make whenever the dock opens (cache the program's own version call); the module never makes it while the dock is closed.
11. **Launching an agent program.** The program learns the app's MCP address and a token made for that tab from its environment or from a file only the caller's user can read (mode 0600), never from its command line. A plain shell tab gets no token. The token is good only while its tab is open. The engine sets the working folder and removes its own secrets from the child's environment.

## Chat

12. **Chat events.** The adapter either gives its own pane (`chat.pane(host)`) and then this clause does not apply, or it gives `status`, `send`, `subscribe` and what it has of `start`, `stop`, `answer`, `modes`, `renderText`. After `subscribe`, the adapter calls `open()`, replays the conversation from its start as events, then sends `state`. Events are those of `DockChatEvent`: `state { running, state, session, mode? }` where `state` is exactly `busy` while a turn runs and any other word otherwise, and `session` is a Claude Code session id usable with resume, or null; `user { text, note? }`; `block { id, kind }` before any `delta { id, text }` for that id; `tool { id, name, summary }` then `tool_result { id, text, error }` (text may be empty); `permission { id, tool, summary }` and `permission_done { id, allowed }` only from engines that ask, which then implement `answer`; `result { ok, text, meta? }` at the end of every turn, also after `stop`; `notice { text }`; `reset` when the conversation was cleared or replaced; `meter { text, high? }` for a usage line. Ids are unique within a conversation. `send` while busy is refused with a message. `start(mode, fresh)` with `fresh` clears the conversation and the session; an engine without modes gets `null` and has no `modes`. `status()` answers `{ installed, version, signedIn, install, running, state, session }`, optionally `mode`, `lead` (a sentence to show in the empty Chat in place of the app's) and `refused` (see clause 13); null means not reachable.

## Refusals and availability

13. **A refusal is not an outage.** The adapter tells the module which it is, through `errors.kind(error)`: `refused` (the engine answered and said no to this caller: the message is shown as it is, and nothing suggests restarting anything), `unreachable` (no answer), `notInstalled` (the program is missing: the install line is shown), `oldEngine` (the route does not exist in this engine), `busy`. Engines use fixed codes for these rather than English text the adapter has to read. `chat.status()` may carry `refused` with the sentence to show.
14. **Availability.** The app can answer cheaply which tabs this caller may use here (`tabs()` is read at mount and on `dock.refresh()`), so a server that allows the dock only to its owner, or an operating system without a PTY, offers fewer tabs or none. `firstRun()` returning false means "not now" for the first-run guide.

## Outside agents

15. **Consent is optional and has two kinds.** An app that gates outside agents by a credential given on its own sign-in page provides neither `consent` nor `storedChoice`, and the module shows no dialog and no Outside agents entry. An app that asks in the window provides `consent`: each request is `{ id, agent, what, offers, always, expires?, escape?, notes? }`. `id` names one waiting call. `agent` is the program's name as the engine knows it, or empty. `what` completes "It asked to ...". `offers` lists the answers the engine can honour, from `deny`, `once`, `always`; the module shows no other. `always` says what a standing yes would cover: `agent` (this program only) or `all` (every outside agent). `expires` is when the engine stops waiting (milliseconds since the epoch). `escape: 'deny'` makes Escape a refusal; otherwise Escape leaves the request unanswered. An answer is for the request with that id and for no other. The engine must be able to say that a request is gone (its caller hung up, its time ran out, another window answered), and the adapter then calls `withdraw(id)`; after a reload of the window the adapter asks the engine which requests are still waiting and shows them again. Only the window can answer. `storedChoice` is the standing setting `ask`, `allowed` or `blocked`, kept by the engine and sealed against changes made outside the app (`changedOutside` reports a broken seal). `blocked` refuses every agent at once, with or without a window, the app's own Chat and agent tabs included.

## Versions

16. **A number, not a missing route.** The engine reports the contract version it implements (this file's module version) where its adapter can read it, so "this engine is too old" is decided by comparing numbers. An adapter maps an older engine onto `oldEngine` errors and onto a smaller `tabs()` set.

## Module 2.1.0: what an adapter may now say

Nothing an engine provides changed in 2.1.0: the sixteen clauses read as they did, and an engine that meets them for 2.0 meets them for 2.1. An adapter written for 2.0.1 compiles and behaves as before; every item here is used only by an adapter that asks for it. The one type that widened is `dock.sendChat(text)`, which now resolves to a boolean (false when nothing was sent).

- **The app's own Chat pane is told what happens to it.** `pane(host)` is still called once, and the object it returns may have `shown()` (the dock is open and Chat is the tab in front), `hidden(why)` with `'tab'` (another tab was chosen or the Chat tab was closed) or `'dock'` (the dock was closed or its host hid it), `closed()` (the Chat tab's cross; the host element is kept and the next show is `shown()` again), `busy()` and `askTarget` (the element the guide's "how to ask" step points at). `send(text)` may answer `false`, or a promise of it, when the text was not taken. The host is `.ft-chat.is-own`, an absolutely placed box that fills the stage with `overflow: auto`; a pane that scrolls by itself fills it (`position: absolute; inset: 0` or `height: 100%`) and manages its own overflow.
- **The ask line beside an own pane**, `chat.ask`. Absent or `'none'`: no ask line on any tab. `'line'`: the module's line on every tab; on Chat the text goes to the pane's `send`, elsewhere it opens Claude Code with the text as `prompt` (clause 4). `{ send(text, tab) }`: the module's line on every tab and every submit goes to that function with the kind of the tab in front. `{ element }`: the app's own element is placed in the slot. The slot is `form.ft-dock-ask`, the same box on every tab; the root has `has-ask-line` while it shows. A busy pane or an answer of `false` leaves the text in the line.
- **First run.** The guide counts the steps it can show. A legacy reader (`placement.storage.legacy.read`) may return `seen: true` with the layout it moves, and `jsonLegacy(keys, true)` from state.ts says it for old keys that hold JSON; without that a moved layout is not taken as seen.
- **Focus at load.** When the dock is restored open before the app has revealed its window, the dock focuses once at the first `class`, `style` or `hidden` change on one of its ancestors that leaves it shown. An app that reveals itself another way (removing a cover, swapping a stylesheet) calls `dock.focus()` after its reveal.
- **Keys in capture-phase listeners.** The module stops keys at its roots in the bubble phase. An app listener in the capture phase starts with `if (dock.keeps(event)) return;`.
- **Notes of a question** (`ConsentRequest.notes`, clause 15) are shown one element each, so each is one whole sentence, already in the person's language or matchable by the app's page translator.
- **Names.** The classes, attributes and tokens an app may rely on are `DOCK_PUBLIC` in adapter.ts and nowhere else; 2.1.0 added the classes `has-ask-line`, `ft-dock-ask`, `ft-dock-ask-own`, `ft-dock-head`, `ft-dock-tab`, `ft-dock-stage`, `ft-icon`, `is-on`, `is-own` and the tokens `--dock-stage-pad`, `--dock-ask-ctl-h`, `--dock-tab-accent`, each token defaulting to the value 2.0 had written.
- **Type check.** Before a module version is cut, and as a step of every port, the folder is compiled with `noUnusedLocals`, `noUnusedParameters`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `noImplicitOverride` and `noImplicitReturns` on.

## Module 2.2.0: the agent kinds are a list, and Antigravity is the fourth

An adapter written for 2.1.0 compiles and behaves as before: copying the 2.2.0 folder into an app changes nothing there until its adapter names a further kind. Every type an adapter uses is the 2.1.0 type unless the adapter gives the type argument described below. `keyHeaders` became optional.

- **The list.** `agents.ts` holds the kinds the module knows: `claude` (Claude Code), `codex` (Codex), `cursor` (Cursor) and `antigravity` (Antigravity, Google's `agy` program), each with its label, its picture and its two sentences. Claude Code keeps its own button, the ask line and the guide. Every other kind gets a head button and a row in the More agents menu.
- **Offering a kind.** A kind is shown when the adapter lists its id in `tabs().builtin` and `agentStatus()` reports it; both. So clause 10's answer may hold further keys, `{ claude?, codex?, cursor?, antigravity?, ... }`, and a key the adapter does not also list is ignored. The module then calls `terminal.open('antigravity', { cols, rows })`, and clause 3's `kind` may be that id. An adapter that adds kinds is typed `DockAdapter<'antigravity'>` (a union for several); `Dock`, `DockTabs`, `DockTerminal` and `DockAgentStatus` follow from it.
- **What the engine needs for a further kind.** Clause 10 for it (found, version, install line, `signedIn` null when it cannot tell, which is always so for Antigravity: it has no status command), clause 4 for its tab, and clause 11: Antigravity reads its MCP servers from a file, so the tab's entry (named `[app]_tab`, with the tab's token) goes into `.agents/mcp_config.json` of the tab's working folder, mode 0600, every other entry kept, and is taken out when the tab closes.
- **A kind that is not in the list** needs no change in this folder: the adapter lists its id, and its status carries `label`. It is drawn with the terminal picture and the sentences of the other programs.
- **`DockProgramStatus.note`** is a whole sentence shown in the kind's menu row in place of the module's (where the engine looked for the program, why it does not start, a step that is not a command). The install line still shows under it.
- **Part names.** Every control of the module carries `data-dock-part`; the attribute and the names are `DOCK_PUBLIC.partAttribute`, `parts` and `partsByKind` (`launch.[kind]`, `menu.launch.[kind]`, `tab.[kind]`). Automation and command layers use these and no class name.
- **A status line for a tab.** A terminal record may carry `status`, and a channel may give `onStatus(handler)` and call the handler with new text ("reconnecting", an exit code). The text of the tab in front shows in the head between the tabs and the buttons, clipped; an empty string clears it.

## The manifest

`MANIFEST.json` in this folder lists the module version and the SHA-256 of every other file here, this one included. The source app (FormVis) writes it; every other app only checks it: read the file names and hashes from the manifest, hash each file's bytes, and fail naming any file that differs, is missing or is extra. The check is small enough to write in any language an app's tools use.
